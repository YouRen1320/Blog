## 关键决策

### 1. sitemap / RSS 在 Nuxt server route 而不是 NestJS

NestJS 是 API server,不该出 XML 内容。Nuxt 已经知道前端路由结构(/articles/:slug 等),sitemap 写在它这边天然合理。RSS 的 channel 元信息也跟前端站点元信息同源。

### 2. 站点设置用 singleton 单行表

vs 通用 KV 表(key/value 字符串)。singleton 行 + 类型化字段:
- 类型安全,Prisma client 直接生成 typed accessor
- AI 字段(threshold int / streaming bool)能 native 校验
- 改字段需要 migration —— 可控,跟代码一起 review

KV 表更灵活但要全部 cast,值不一致风险大。当前 9 个字段是稳定的,不需要灵活性。

### 3. 评论必须邮箱 + 默认 PENDING

匿名评论(只填昵称)+ rate limit 容易被 bot 滥用。邮箱必填不解决 bot,但提供:
- 后续可用作 gravatar(可选)
- 反垃圾时可以邮件去重 / 黑名单
- 不显示给公众,只 admin 可见

PENDING 默认让我永远是评论的最终把关人,垃圾被 admin 删除即可,APPROVED 评论才进 RAG 检索面(未来如果引入)。

### 4. 评论 schema 已经有 parentId,但前端不开启嵌套

数据模型一次到位,UI 慢慢加。如果未来想做嵌套回复,直接在 CommentSection / Comments.vue 改渲染,后端 `parentId` 已校验属于同文章 + 已 APPROVED。

### 5. 反垃圾不用 captcha

- 单人博客流量极小,垃圾量可控
- captcha(reCAPTCHA / hCaptcha)需要第三方服务 + JS 加载
- 现在就 rate limit + 长度 + 默认 PENDING 三道,够用
- 真出现垃圾洪水再加 captcha 不晚

## 踩坑(详见 journal)

按时间顺序:

1. **服务器 git pull GitHub 又超时**:延续 V1.1 教训,直接 tar + scp(33 KB,2 秒到)
2. **tailwind oxide UTF-8 panic**:docker 容器里 @tailwindcss/oxide 在多线程处理含中文的 .vue 时 byte-slice panic(`vue.rs:18:59 Utf8Error{valid_up_to:45}`),4.1.18 / 4.2.4 都没修。改 Web Dockerfile **本地 build → 镜像 COPY .output**,绕过 oxide
3. **NestJS @Query type intersection 不被 reflect**:`PaginationQueryDto & {status?:...}` 的写法让 ValidationPipe 拿不到 class metadata,`@Type(() => Number)` 不执行,page/pageSize 是 undefined → `(undefined-1)*undefined=NaN` → Prisma `skip missing`。修法:用 `class extends PaginationQueryDto` 单独 DTO
4. **Prisma 6.19 `$transaction([count, findMany])` + self-relation 边界 bug**:Comment 自指 relation 让 batch 模式 schema 验证错位,把 findMany 的 skip 提示报到 count 里。改成顺序两个 await 绕开
5. **生产 mock 数据 slug 是 hello-blog 不是 first-light**:第一次测评论时用错 slug 报 404,改对就通了
