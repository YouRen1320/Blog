# ADR 0001:版本切片策略

**日期**:2026-05-05
**状态**:已采纳

## 背景

项目目标范围很大:
- 5 个应用(api / admin / web / mobile / ai-service)
- 3 类客户端(网页 / 移动 / 后台)
- 2 个跨语言栈(TypeScript + Python + Dart)
- 还要包含部署 + 监控

如果一开始就线性推进每个应用,很容易陷入"一切都没法跑"的状态半个月。所以需要切版本。

## 选项

### 选项 A:按"模块/技术栈"切版本
比如 V1 = 全部数据库,V2 = 全部 API,V3 = 全部前端,V4 = 全部移动端...

**问题**:每个版本都跑不通主链路,验收只能看代码,看不到产品形态。失去成就感,也失去发现问题的能力。

### 选项 B:按"主链路完整度"切版本(已采纳)
V1 = 本地能跑通最小博客主链路,V2 = 上线,V3 = 加移动端入口,V4 = 加 AI 生产。

每个版本都是一个**可演示、可使用**的产品形态。

### 选项 C:按"功能丰富度"切版本
V1 = 最小博客,V2 = 加评论,V3 = 加专题,V4 = 加多语言...

**问题**:跟项目初衷(AI 内容生产)关系不大,把精力浪费在博客的二级功能上。

## 决定

采用 **选项 B —— 主链路驱动**。

每个版本必须满足:
1. 端到端跑得通(哪怕功能很少)
2. 能演示
3. 比上一版多一个用户能感知到的能力维度

## 后果

正面:
- 每个版本结束都有可见成果,容易判断是否走偏
- 早期就发现集成问题
- 部署相关的痛苦提前到 V2,而不是堆到最后

负面:
- 早期可能要写一些"垫片代码"先让链路跑通(比如 V1 的简化登录),后续要回头加固
- 跨版本重构难免

接受这些代价,因为 vibe coding 项目最大的失败模式是"最后才上线发现整个跑不动"。
