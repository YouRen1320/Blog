**日期**:2026-05-05
**任务**:#55 ~ #63
**状态**:已完成

> 用户问:"国外的 AI 全栈是不是所有的技术栈都写在这个项目里?"
> 答案是**没有**。这一版补的是国外 AI-native 项目的 8 项标配。

## 背景与判断

V1.0 ~ V1.3 已经做的是"经典全栈博客 + 基础 AI 集成":pgvector + LangGraph + 真 LLM。这放在 2026 年的 AI-native 招聘标准里是合格 mid-level,但缺几个 senior / staff 级项目里默认存在的工程能力:

1. 流式 UI(用户感知 LLM 在思考,不是黑盒等 30 秒)
2. 多模型路由(代码无关 provider,一行 env 切换)
3. 高级 RAG(reranking)
4. Prompt 追踪(成本 / 质量回归)
5. Eval 框架(防 prompt regression)
6. 全栈可观测性(不只是 AI 链路)
7. Agent 高级模式(checkpoint / human-in-the-loop)
8. 真 e2e(浏览器跑通完整主链路)

## 为什么不做 Modern stack 重写 / 平台切换

用户原本提到 13 项,我筛掉 5 项放 v2.0:

- **Next.js + Bun + Drizzle** 重写:全栈推翻,数周工作量
- **Serverless 部署**(Vercel / Fly.io):平台切换,运维改造
- **Multimodal**(图 / 音 / 视频):新功能模块,要选具体场景
- **Object storage**(S3 / R2):新增基础设施
- **tRPC**:RPC 协议切换

这些都是**架构级改动**,不该跟 v1.4 这种"工程能力补完"混做。等 v2.0 时如果用户想做 modern stack 完整重写就一起来。

## 关键决策

### 1. 流式输出走 free-form markdown 而不是 streaming tool calling

OpenAI 协议**理论上**支持 streaming + tool calling(tool_call.arguments 是 partial JSON,逐 chunk 累加),但解析 partial JSON 在 v1 阶段成本不值得 —— 半个 JSON 在中间什么都说明不了。

改让 LLM 按"约定 markdown 结构"输出:

```
# 标题
> 摘要
## 二级标题
正文...
---
tags: a, b, c
```

流末用 regex 一次性 parse,流过程中前端只需 append text。简单且可观:用户能看到完整生成过程。

### 2. 内联 AI chunk 累积用 before/after 固定法

**反例**(我第一版差点踩):每次 chunk 来时算 offset:
```ts
post.content = post.content.slice(0, insertOffset) + acc + post.content.slice(insertOffset + acc.length - chunk.length)
```
content 长度变就错位,offset 跟踪一团乱。

**正解**:流前固定 before / after 两段:
```ts
const beforeContent = post.content.slice(0, selStart)
const afterContent = post.content.slice(selEnd)
let acc = ''
// 每个 chunk:
post.content = beforeContent + acc + afterContent
```
任何长度不变,边界永远正确。这是"不要在循环里追踪状态"的经典体现。

### 3. LiteLLM + LangFuse 都 0 侵入

业务代码完全不知道在不在追踪。**callback 模式 / instrumentation 模式** 是 modern AI 工程的最佳实践:不在业务代码里手写 log / trace,靠 SDK auto-collect。

这个原则跟 V1.2 加 LangSmith 一致(LangGraph 自动检测 LANGCHAIN_TRACING_V2)。

### 4. Reranker 选 BGE-reranker-base(1GB)

中文友好 + 单人博客可接受。降级路径已写在代码注释:`jinaai/jina-reranker-v1-turbo-en`(150MB)在生产嫌大时切换。

### 5. checkpoint 选 MemorySaver(进程内)

代码注释里写了 SqliteSaver 切换方法,但默认 MemorySaver 简单 + 无状态依赖。生产想跨重启持久化几行改完。

### 6. e2e 改密码只测错路径

200 路径靠 jest 单测覆盖。e2e 真改 admin 密码会:
- 后续 e2e 全部登录失败
- strict 限流 5/min,几次试探就 429
- 测试套间互相污染,排查困难

测错路径已经验证"前端校验 + 后端 401/400 + UI 提示"完整链路,200 路径的"hash + 写库"是 service 层逻辑,jest 验证更精准。

### 7. promptfoo 锁定 0.119.0

最新 0.121.9 要求 Node 22.22+,我们环境 22.14。**锁旧版本而不是升 Node**:升 Node 是用户环境改动,影响别的项目;锁版本只影响本项目。

## 学到的

- **可观测性是免费的**:LangFuse / LangSmith / OTel 都能做到 0 业务代码侵入。**默认开**没什么坏处,关掉只省 5% CPU。早开比晚补好
- **流式 UI 的成本是 prompt 工程**:一旦改成 free-form markdown,LLM 不一定严格遵守"# 标题 / > 摘要"格式。需要 system prompt 强约束 + parse fallback。比 tool calling 多了"信任 LLM 跟随结构"的风险
- **Reranker 是 RAG 的标准答案**:retrieve top-K 召回宽 + cross-encoder 精排,这是 2024 起几乎所有 RAG 项目的范式。bi-encoder 一次性出 top-3 是早期做法
- **Eval 不是测试**:eval 测的是"输出质量",答案是模糊的(不像 unit test 0/1 通过)。LLM-as-judge 是关键工具,虽然贵但比人工审核可扩展
- **Agent checkpoint 比想象中简单**:LangGraph compile 时传 checkpointer,调用时传 thread_id 就完了。复杂的是后续 human-in-the-loop 节点设计,但**前置基础设施(checkpoint)不该等真要 HIL 时再做**
- **e2e 是产品级测试**:它跨整个技术栈跑(数据库 + 后端 + 前端 + 浏览器),发现的 bug 通常是"集成层面"问题(JWT 没传、CORS 错、SSR 渲染时机)。jest 单测找不到这种
- **不要混改 Node 大版本**:promptfoo 升级要求 Node 22.22+,我直接锁版本而不是升 Node。生产环境变更应该一次只改一件事

## 给学习者的提醒

- 想做 AI-native 项目,**先做流式 UI**:用户体验差距太大,而且强制你掌握 SSE / streaming 协议
- **LiteLLM 几乎是标配**:除非你能确定永远只用一家 provider(实际从来不会)
- **不要把 callback 模式当"花拳绣腿"**:LangFuse / LangSmith / OTel 这套追踪起来后,debug 一个慢请求 30 秒变 30 秒(看 trace),不是黑盒猜
- **eval 框架先建后用**:第一个 case 写好就好,后面随用随加。不要等"我有 100 个 prompt 时再开始"
