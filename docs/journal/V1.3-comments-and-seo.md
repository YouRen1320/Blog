# V1.3 站点设置持久化 + 评论系统 + SEO(整体)

**日期**:2026-05-05
**任务**:#51 ~ #54
**状态**:已完成
**Tag**:v1.3.0

> V1.3 不是"新功能阶段"而是"产品角落补完"。三件事:让搜索引擎能爬到博客(sitemap+RSS)、让站点元信息能在后台改(SiteSetting)、让博客有评论(Comment)。看似零碎,但加完之后博客是个真正的"个人发布平台",不只是 AI 玩具。

## 选这三件一起做的逻辑

1. 三件都是"用户报告里说要做没做"的项,用户说"全部做掉"
2. 三件之间**几乎没耦合**,可以并行设计 + 各自验收
3. 工作量梯度:sitemap+RSS 30 分钟,Settings 1.5 小时,评论 3 小时。先做小的清掉信心,大的留最后

## 关键决策

### 1. sitemap / RSS 在 Nuxt server route,不是 NestJS

NestJS 是 API,不该负责 SEO 元数据。Nuxt 已经知道前端路由结构(`/articles/:slug`、`/categories/:slug` 等),sitemap 在 web 端写最自然。RSS 的 channel 元信息(标题、描述、语言)也跟前端站点元信息同源。

### 2. SiteSetting 用 singleton 单行表

candidate:
- A. **单行表** + 类型化字段(选)
- B. KV 表(`key/value` 全 string)
- C. 把配置塞 .env 重启生效

A 类型安全,Prisma 直接生成 typed accessor,AI 字段(int/bool)能 native 校验。改字段需要 migration 但每次都跟代码一起 review,可控。

B 灵活但全部 cast,值不一致风险大,UI 校验和后端解耦。当前 9 个字段稳定,不需要这种灵活性。

C 不让用户改,违背"后台 Settings 页是给非工程师用的"初衷。

### 3. settings 公开/私有分两个 endpoint

```
GET /settings        -> { title, tagline, icp }              (public)
GET /admin/settings  -> 全部字段                                (admin)
PATCH /admin/settings                                         (admin)
```

不让 web 端拿到 AI 模型 / JWT 配置等"实现细节"。这是前后端最小权限原则的微观体现。

### 4. 评论必须邮箱 + 默认 PENDING + 不强制登录

匿名评论(只填昵称)+ rate limit 容易被 bot 滥用。邮箱必填:
- 不公开(后端 `publicCommentSelect` 显式排除)
- 后续可作 gravatar 头像源
- 反垃圾时邮件去重 / 黑名单

PENDING 默认让我永远是评论的最终把关人。垃圾被 admin 删除即可,APPROVED 评论才进 web 端可见区。如果未来引入"评论加入 RAG 训练数据" 的功能,APPROVED 状态也是天然的过滤器。

### 5. 反垃圾不上 captcha

- 单人博客流量小
- captcha 要第三方服务 + JS 加载,体验差
- 现在 rate limit(5/min)+ 长度 1-1000 + 默认 PENDING 三道够用
- 真出现垃圾洪水再加不晚

### 6. 评论 schema 留 parentId 但 UI 不开嵌套

数据模型一次到位 + UI 慢慢加。后端校验 parentId 必须属于同文章 + 已 APPROVED(防伪造嵌套)。前端要不要嵌套是 UI 决策,改组件即可。

### 7. web 端 Dockerfile 改"镜像外 build"

V1.3 加评论组件后,docker 容器里 @tailwindcss/oxide 触发 UTF-8 byte-slice panic。试了:
- 升级 4.2.4 → 仍然 panic
- 降级 4.1.18 → 仍然 panic
- 改 base image alpine → slim glibc → 仍然 panic
- `@source not "**/*.vue"` → 没生效(可能 vite plugin 优先级)
- 改 vue 文件开头 → 仍然 panic(因为 oxide 是多线程切 chunk,不是单文件)

最后选**镜像外 build**:本地 macOS `pnpm build` 出 `.output`,docker 镜像只 COPY 这个目录。流程变得不"标准"但稳定可控。

## 踩坑

### 1. NestJS @Query type intersection 不被 reflect

```ts
// ❌ 这样写 NestJS reflect 拿到的是 Object,ValidationPipe 不会 transform
list(@Query() query: PaginationQueryDto & { status?: CommentStatus }) {}

// ✅ 必须 class extends
class CommentListQueryDto extends PaginationQueryDto {
  @IsOptional() @IsEnum(CommentStatus) status?: CommentStatus;
}
list(@Query() query: CommentListQueryDto) {}
```

错误的写法让 `page` / `pageSize` 还是字符串 / undefined → `(undefined - 1) * undefined = NaN` → Prisma 收到 `skip: NaN`(序列化为 null) → 报 `Argument skip is missing`。

教训:**type intersection 是 type-level 的,运行时 reflect-metadata 看不到**。NestJS / class-validator 全套都依赖运行时元数据,DTO 必须是真 class。

### 2. Prisma 6.19 `$transaction([count, findMany])` + self-relation 边界 bug

`Comment` 有 `parent` self-relation。在 `$transaction([count(...), findMany(... skip ...)])` 这种 batch 模式下,Prisma 6.19 偶发把 findMany 的 skip 提示错位到 count 的 schema 上,报 "Argument skip is missing" 假错误。

修法:拆成顺序两个 await(`const total = await count(...)` 然后 `const data = await findMany(...)`)。性能上多一 round trip,但单人博客流量这个差异忽略不计。

### 3. Tailwind oxide 在 docker 里 panic

`vue.rs:18:59 Utf8Error{valid_up_to:45}` 这个 panic 发生在多线程处理 chunk 时,**byte slice 落在中文字符中间**触发。这是 oxide 真 bug,4.1.x / 4.2.x 都没修。改 base image / 升降级版本都没用。最后选"绕过":本地 build 出 `.output`,镜像只 COPY。

### 4. 服务器 git pull 又超时

延续 V1.1 教训,GitHub 在境内对长 TCP 连接非常飘。直接 `tar | scp | tar -xzf`(33 KB 文件包)2 秒到位。

## 学到的

- **DTO 千万别用 type intersection**:运行时 reflect 看不到,所有依赖元数据的工具(class-validator / class-transformer / NestJS Pipe)都失效。永远用 `class extends`
- **Prisma `$transaction([...])` 不是免费的**:批处理模式下 schema 验证有时会错位,在 self-relation / 大复杂度模型上偶发出问题。改成顺序 await 在低流量场景没成本
- **Native binary tools 跨平台风险**:tailwind oxide 是 Rust native binary,跨 architecture / libc 行为不一致。被它逼得改 Dockerfile 流程值得 — 长远来看"build 完整产物在外、镜像只跑"也是更标准的部署模式(类似 buildpack 或 Vercel/Netlify)
- **服务能在不修代码情况下变可观测**:LangSmith(V1.2)纯环境变量,sitemap/RSS 也是几个 server route 的事,这些"小工程"加完之后博客的"工程化感"明显提升
- **小事一起做**:三件事一起做比分三个版本节省至少一半时间(共用一次 build/部署/测试 cycle)。但前提是它们之间没耦合 — 有耦合的话拆开做才安全
- **写完整功能 vs 写半套**:评论系统选了"完整审核流"(PENDING/APPROVED/REJECTED + admin 页),没偷懒直接 APPROVED。多花 30%时间换 100% 完整功能,值
