# V1.x —— 测试者账号(USER role)

**日期**:2026-05-08
**任务**:给生产环境加一个最低权限账号,拿给测试用户体验,核心约束:能写、能用 AI、不能发布、AI 每天 3 次。
**状态**:已完成

## 目标

线上原本只有一个 ADMIN 账号,产品想做"游客试玩"。验收:

- tester 用预填邮箱密码可一键登入 admin
- tester 能写文章、能传图、能用 AI
- tester **永远发不了**(后端 + 前端双重挡)
- tester 调 AI **第 4 次起 429**(北京时间日切重置)
- tester 进 admin 看不到不属于他的菜单(分类/标签/评论审核/用户管理/设置/统计)
- 自己的 ADMIN 流程不受任何影响

## 关键决策

### 1. 角色不新增,直接复用 `USER` 枚举

`UserRole` 早就有 `ADMIN | USER` 两档,但 `USER` 一直空挂——单作者模式,公开注册关着,没人会落到这个角色。

备选:加 `EDITOR` / `TESTER` 枚举值。但这要走 prisma migrate + 改 union type,语义上跟"非管理员的登录用户"完全重合,纯属增项。**复用 `USER` 不动 schema,代码里只改装饰器即可**。

将来如果出现"游客阅读但不能写"这种第三档,再考虑是否拆。

### 2. AI 每日配额选**内存 Map**,不上 DB

这是个 3 次/天/USER 的量级限额。三种实现:

| 选项 | 改动量 | 持久性 | 审计 |
|---|---|---|---|
| nestjs-throttler 改 24h TTL | 最小 | 容器重启清零 | 无 |
| **自定义内存 guard**(选这个) | 小 | 容器重启清零 | 无 |
| DB 表 + 计数 | 中 | 持久 | 有 |

容器重启重置 3 次,不构成滥用风险。审计需求目前没有,Demo 流量极低。**这种规模上 DB 是过度设计**。

未来如果需要看"测试者用了哪些 prompt",再加 `AiUsageLog` 表,本次先不做。

### 3. 配额按**自然日**(北京时间)切,不用滚动 24h

滚动 24h 实现更简单(只需 timestamp),但用户直觉是"一天 3 次,明天再来"。23:59 用 3 次的人 00:01 还能再用一次更符合常识。

实现:`new Date(Date.now() + 8*3600*1000).toISOString().slice(0,10)` 拿到北京日期串作 key。容器跑在哪个时区都不影响。

### 4. 配额跨 3 个 AI 入口**共享**,不是每个入口各 3 次

drafts/stream / inline / transcribe 全算同一个桶。否则用户算账要算"每个按钮各 3 次合 9 次",反直觉。守卫挂在 controller 级 `@UseGuards(AiDailyQuotaGuard)`,所有方法共享一个 Map。

(原本还有非流式 `POST /admin/ai/drafts`,这次顺手砍了——见下条。)

### 4.1 顺手砍了非流式生成入口

AIInbox 原本有"生成草稿"和"流式生成"两个按钮。非流式入口同步调 ai-service 等完整响应,LLM 慢的时候 90s 撞超时,产线已经报"请求超时,请稍后重试"。

流式 SSE 既快又能让用户看到进度,功能上是非流式的超集。**留着两个只会让用户挑错**。

砍掉:
- 前端按钮 + `onGenerate` + `generating` ref + `generateAiDraft` API 函数
- 后端 `POST /admin/ai/drafts` 路由 + `AiService.createDraft` + 私有的 `callAiService`(非流式 fetch 实现)

只剩流式 + inline + transcribe 三个入口,文档 / 配额计数 / 注释一并对齐到"3 个"。

### 5. ADMIN 完全跳过配额

guard 第一句 `if (user.role === 'ADMIN') return true`,不计数不查桶。理由:配额服务的对象是测试者,作者自己不该被限。

### 6. publish/unpublish 锁 ADMIN——不是 status 字段消毒

`@Roles('ADMIN')` 直接挂在 publish/unpublish 路由上即可。

确认了一下 `CreateArticleDto` / `UpdateArticleDto` **不接 status 字段**——USER 没法 POST `status: PUBLISHED` 绕过路由。所以 service 层不需要再消毒。少改一个地方。

唯一往 PUBLISHED 写的路径就是 `articles.service.publish()`,现在 controller 把它锁住,USER 走不到。

### 7. 上传放给 USER,但上传目录权限要修

跟这个任务并行,Dockerfile 里 `/app/uploads` 是 named volume 挂的,镜像里目录不存在 → 挂载时 owner 是 root → nodejs UID 1001 写不进去 → EACCES。

修复(已做):Dockerfile 在 USER nodejs 切换前 `mkdir -p /app/uploads && chown -R nodejs:nodejs /app`。**已存在的 volume 不会被重建权限**,所以服务器上要么删 volume,要么 `docker exec -u root chown` 一次。详情见 [V1.x-uploads-eacces.md(若有)] 或本次 commit 历史。

### 8. 测试账号密码不当 secret 处理

要"一键登入",密码必须打进 SPA bundle。任何人 view source 就能拿到。

那就**主动接受**:把它当公开 demo 凭证。Login.vue 里直接 hardcode `tester@iyouren.top` / `tester12345`,seed 脚本 fallback 默认值也对齐。源码 + git 历史都明文。

只要这个账号始终是 `role=USER`(seed 脚本每次跑都强制 set 回 USER),它的能力上限就被代码约束死。

### 9. seed 脚本写成 `.cjs` 而不是 `.ts`

生产 Docker 镜像只装 prod 依赖,**ts-node 在 devDependencies 不会被打进去**。两条路:

- 写 `.ts` + `tsx` 编译进 dist:nest build 的 entry 是 main.ts,要把 scripts 也编译要改 nest-cli.json 或加单独的 tsconfig.scripts.json,工程量超过收益
- **写 `.cjs`,直接 `node` 跑**:`@prisma/client` 和 `bcryptjs` 都在 prod deps 里,纯 CJS 直接 require 就工作

选第二条。Dockerfile 多一行 `COPY apps/api/scripts ./scripts`,完事。

### 10. Login 后跳转按角色分流

ADMIN → `/dashboard`(原行为);USER → `/articles`(因为 dashboard 对 USER 是 adminOnly,直跳过去会被 guard 弹回,体验是闪一下)。

router.beforeEach 多加一条:`to.meta.adminOnly && user.role !== 'ADMIN'` → 强制跳 `/articles`。前端双重防护——后端各 controller 各自 `@Roles('ADMIN')` 兜底,即使 USER 直接敲 URL 也只能拿 403。

## 踩坑 / 注意

### 上传 EACCES 同时暴露的 Docker volume 老问题

修了 Dockerfile 的 mkdir + chown,但服务器上**已经存在的** `blog_blog_uploads` volume 不会被重新初始化 owner——必须 `docker volume rm blog_blog_uploads`(空的话直接删,有图就 `docker exec -u root chown`)。

否则镜像层 owner 对了,运行时挂载点还是 root。

### compose `--env-file` 必须每次都带

`.env.production` 不是 `.env`,docker compose 默认只读 `.env`。每条 ps/exec/logs 都得带 `--env-file .env.production`,不然 yaml 里的 `${VAR}` 全空,**容器拿到的 DATABASE_URL 是空串**,连不上 Postgres。

兜底建议:`ln -s .env.production .env` 做软链,或在 ~/.bashrc 加 alias `dcp='docker compose -f /opt/blog/docker-compose.prod.yml --env-file /opt/blog/.env.production'`。

### admin 编辑器对 USER 不要错放发布按钮

`v-if="post.status !== 'PUBLISHED'"` 是按文章状态切的,不是按用户角色。USER 永远只能看到草稿(他的文章只能 DRAFT),所以单纯加 `v-if="isAdmin"` 在外面 `<template>` 包一层就够,不用动原有逻辑。

后端兜底是关键——前端再隐,USER 直接 `curl -X PATCH /admin/articles/:id/publish` 仍然要被 403 拦下。两道线。

### Dashboard 对 USER 是 adminOnly,但路由默认 `/` → `/dashboard`

USER 输入根 URL 会被 guard 弹回 `/articles`。Login 成功后我也改成按角色 fallback,避免闪一下。

## 给学习者的提醒

- **复用现有枚举优于加新枚举**:每个新枚举值都是一个迁移 + 一片连锁改动。如果"非管理员"的语义就是你要的,USER 已经在那了。
- **配额放内存的前提**:量级低 + 容器重启可接受。一旦上 1k+ 用户或要审计,DB 是必须的——别把内存方案当万能。
- **demo 凭证不要假装它是 secret**:能打进 SPA 的就是公开的,坦然 hardcode 比藏在某个看似安全的地方更让人放心。生产防线靠的是这个账号本身的权限上限,不是密码强度。
- **Docker named volume 的权限初始化只发生在 volume 第一次创建**:后续重启都拿 volume 已有 owner,镜像 chown 不会传递过去。运维侧要有 fallback 命令(rm volume 或 exec chown)。
- **前端权限隐藏永远不是真权限**:任何 v-if/v-show/menu filter 都只是"省得用户点错",真锁是 controller 上的 `@Roles`。两层都要做,但只信任后端那层。
